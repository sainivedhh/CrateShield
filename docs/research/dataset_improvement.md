# Identifying and Preparing a Better Dataset

> **Scope:** This document audits the current dataset (`data/dataset.json` and `data/synthetic_crates/`) and proposes concrete improvements for class balance, diversity, and leakage prevention.

---

## 1. Current Dataset Audit

An inspection of `data/dataset.json` and the synthetic generation logic reveals a heavily skewed dataset.

**Class Balance:**
- **Total Crates:** 555
- **Benign:** 100 (Sourced from top crates.io packages)
- **Malicious:** 455

**Sourcing Breakdown for Malicious Crates:**
- **Real (RustSec):** ~55 (Many are yanked/unavailable, so active signal files are fewer).
- **Synthetic:** 400 (Generated by `ingestion/synthetic.py`).

**Leakage Risks:**
The synthetic crates exhibit strong naming patterns that an ML model could easily exploit:
- `syn_buildrs_*`
- `syn_procmacro_*`
- `syn_depanomaly_*`

If the crate name is included in the feature set (e.g., via a Bag-of-Words or direct text embedding), a model will learn to predict `MALICIOUS` simply by observing `syn_` in the name, entirely bypassing the actual code signals (build.rs AST, unsafe counts).

## 2. Proposed Additions

To make the dataset robust enough for fine-tuning or rigorous evaluation:

1. **Massive Benign Expansion:** 100 benign crates is insufficient to represent the diversity of legitimate Rust code. We must expand this to at least 1,000–5,000 benign crates. This should include not just the "top 100" but a stratified sample across downloads (high, medium, low) to ensure the model doesn't just learn that "popular = benign".
2. **More Diverse Malicious Patterns:** `synthetic.py` relies on a small pool of IPs, commands, and domains. Real malware uses obfuscation, nested macros, and staged payloads. The generator should be updated to use realistic obfuscation (e.g., base64 encoded command strings, hidden hex arrays).
3. **Real-world False Positives:** We should intentionally source benign crates that *look* malicious (e.g., `cc`, `bindgen`, system utilities that spawn processes heavily) and label them `BENIGN`. This forces the model to learn context, not just count process spawns.

## 3. Train/Validation/Test Split Strategy

Because the vast majority of malicious data is synthetic and template-driven, random splitting will cause severe data leakage (e.g., `syn_buildrs_1` in train, `syn_buildrs_2` in test—they share identical structure).

**Proposed Strategy:**
- **Test Set:** 100% Real-world data. All valid RustSec advisories and a randomly selected holdout of real benign crates. **Zero synthetic crates in the test set.**
- **Training Set:** The 400 synthetic crates, plus the remaining benign crates.
- **Validation Set:** A mix of synthetic and benign, ensuring no overlap in the specific parameterized templates (e.g., if a specific IP/domain pool is used in training, a different pool is used for validation).

This guarantees that high test-set accuracy reflects actual malware detection capability, not just memorization of the synthetic generator's templates.
